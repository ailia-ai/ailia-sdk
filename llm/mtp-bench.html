ailia LLM MTP ベンチマーク

ailia LLM 1.5.1 の MTP（Multi-Token Prediction）で、Qualcomm SoC の NPU における Gemma 4 の Decode スループット（TPS）がどれだけ改善するかを示します。

MTP の仕組みと使い方は ailia LLM MTP ガイド、MTP を使わない QNN の測定結果は ailia LLM NPU（QNN）ベンチマーク を参照してください。

  • 結果の概要
  • Android（Snapdragon 8+ Gen 1 / SM8475、Snapdragon 7s Gen 3 / SM7635）
  • Windows（Snapdragon X Plus / SC8380XP）

結果の概要

  • NPU のテキスト生成（Decode）は、MTP により Gemma 4 E2B で 1.44〜1.55 倍（SM8475 / SM7635 / SC8380XP）、SC8380XP の E4B で 1.70 倍 高速になりました。SM7635 の E4B は 1.02 倍です。
  • E2B の画像入力（VLM）でも 1.36〜1.50 倍、出力が予想しやすい音声の書き起こし（ALM）では 2.4〜2.6 倍 高速になりました。
  • QNN 単体では CPU を下回ることがあった NPU の Decode が、MTP により Android で CPU と同等以上 になりました。Snapdragon 7s Gen 3 の E2B ではテキスト生成で CPU の 1.63 倍、音声入力で 2.85 倍です。
  • Prefill（プロンプト処理）と TTFT は MTP の有無でほぼ変わりません。

Android

テキスト生成の Decode スループット

81 トークン入力・1,000 トークン生成時のスループットです。CPU は同じ端末で同一の Q4_0 GGUF を標準の llama.cpp 経路（MTP なし）で実行した値です。受理率は、Assistant が提案した候補のうち本体の検証で採用された割合です。

SM8475（Hexagon v69）E2B / FP169.971 tokens/s6.947 tokens/s10.024 tokens/s1.44 倍高速0.70 倍 → 1.01 倍33.7%
SM7635（Hexagon v73）E2B / Int166.045 tokens/s6.393 tokens/s9.877 tokens/s1.55 倍高速1.06 倍 → 1.63 倍35.6%
SM7635（Hexagon v73）E4B / Int163.351 tokens/s3.127 tokens/s3.189 tokens/s1.02 倍0.93 倍 → 0.95 倍39.1%

E2B では SM8475・SM7635 とも 1.4〜1.6 倍に向上しました。受理率は 35% 前後ですが、Assistant の 3 候補と本体の 4 行検証を 1 回の AR-4 で処理するため、本体 1 回あたりの確定トークン数が増えます。SM7635 の E4B はテキスト生成では 1.02 倍にとどまりました（音声入力では 1.76 倍）。

MTP ありのグラフは、本体 1 回の実行（ラウンド）の所要時間を、そのラウンドで確定したトークン数で均等に割り当てて描いています。候補が多く受理されたラウンドでは TPS が高く、すべて外れたラウンドでは低くなるため、値が上下に振れます。凡例の TPS は全体の合計時間から計算した値です。

TTFT（最初のトークンまでの時間）

TTFT はプロンプト設定と最初の生成呼び出しの合計で、モデルのオープンは含みません（greedy、中央値）。

Prefill は MTP の有無にかかわらず AR-256 で処理するため、TTFT はおおむね同程度です。画像入力では、エンコーダ実行前に Assistant を解放し、Prefill 後に再生成する処理が加わります。各試行は新しいインスタンスで初回の生成を測定しており、マルチターンでの KV 再利用は含みません。

CPU との比較

QNN ベンチマークでは、NPU は Prefill で CPU の最大 4.2 倍高速でしたが、1 トークンずつ処理する Decode では重みの読み出しが支配的になり、CPU と同等か下回っていました。MTP では本体の 1 回の実行で複数トークンを確定できるため、NPU の Decode が CPU を上回ります（上記の表の「CPU 比」）。

  • SM7635 の E2B では、テキスト・画像・音声のすべてで NPU が CPU を上回り、テキスト生成で 1.63 倍、音声入力で 2.85 倍です。
  • SM8475 の E2B では、MTP なしでは CPU の 0.70 倍だったテキスト生成が、MTP により CPU と同等（1.01 倍）になりました。音声入力では 1.66 倍です。
  • 音声入力では、Android の全構成で NPU が CPU を上回ります。
  • SM8475 E2B の画像入力と、SM7635 E4B のテキスト・画像入力は、MTP ありでも CPU をわずかに下回ります。
  • NPU は Prefill が CPU より大幅に速く、Prefill 中の CPU 使用率も 3% 前後に収まるため、TTFT や発熱、他の処理への影響を含めた総合的な性能では NPU が有利です。

CPU は同じ端末で同一の Q4_0 GGUF を標準の llama.cpp 経路（OpenMP 無効、MTP なし）で実行した過去の測定値で、テキストは 2 回、画像・音声は各 1 回の測定です。音声入力の CPU 値は、33 トークン出力の記録から先頭 32 トークンの時間を使って再計算しています。CPU と NPU は測定時期と生成されたトークン列が異なり、クロック・温度も固定していないため、目安として参照してください。

CPU での MTP について: MTP は CPU でも利用できますが、SM7635 の CPU で測定したテキスト生成では MTP なし 5.830 tokens/s に対し MTP あり 5.341 tokens/s（0.92 倍）で、高速化しませんでした。CPU では 1,000 トークンの出力に対して本体で 1,960 行を検証し、Assistant も 1,470 回実行するため、追加の演算を回収できませんでした。MTP の効果が大きいのは、複数行の処理を効率よく並列化できる NPU です。

測定条件

Snapdragon 8+ Gen 1（SM8475 / Hexagon v69）は E2B の FP16 モデル、Snapdragon 7s Gen 3（SM7635 / Hexagon v73）は E2B / E4B の Int16 モデルを使用しています。本体・Assistant とも v1.5.1 の MTP 対応モデル（W4）で、QAIRT 2.47、コンテキスト長 8192、AR-256（Prefill）/ AR-4（検証）/ AR-1 構成です。

「MTP なし」は同じ MTP 対応の本体を Assistant なしで実行した値（AR-1 で 1 トークンずつ生成）、「MTP あり」は Assistant を ailiaLLMOpenMtpModel で開いた値です。各条件は off → on → on → off の順に 2 回ずつ測定し、中央値を示します。各試行は新しいインスタンスで実行し、試行間に 20 秒の間隔を置いています。TPS は最初の出力トークンを除いた時間から計算しています。

サンプリングは greedy（temperature 0、top-k 1、top-p 1、seed 1234）です。temperature ありの結果は「temperature ありのサンプリング」を参照してください。MTP と AR-1 では生成されるトークン列が異なるため、同一トークン列での比較ではありません。

Windows

測定条件

Snapdragon X Plus（SC8380XP / Hexagon v73、8 コア）の Windows 11 Pro 上で、E2B / E4B の FP16 モデルを測定しました。同じ端末・同じビルドで、次の 3 構成を比較しています。

  • 非 MTP：v1.5.0 の従来モデル（gemma4-<model>-sc8380xp.qnn）
  • MTP なし：v1.5.1 の MTP 対応本体を Assistant なしで実行（AR-256 / AR-1）
  • MTP あり：v1.5.1 の MTP 対応本体 + Assistant（AR-256 / AR-4）

各構成 1 回の測定で、各試行の前に 60 秒待機しています。AC 接続、バランス電源プラン、4 つの高性能コアをワーカーとして使用し、背景アプリが動作している状態での測定です。
