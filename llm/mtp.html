ailia LLM MTP（Multi-Token Prediction）ガイド

ailia LLM 1.5.1 で対応した MTP を使用して、Gemma 4 のトークン生成を高速化する方法を説明します。

このページは ailia LLM NPU（QNN）ガイド からの差分として、MTP に必要なモデルと API を説明します。NPU のセットアップ（QNN ランタイムの配置、Android の設定、SoC 名の取得）は QNN ガイドと共通です。測定結果は ailia LLM MTP ベンチマーク を参照してください。

MTP とは

LLM は通常、1 回の推論で 1 トークンずつ文章を生成します。次のトークンは直前までのトークンに依存するため、1,000 トークンを生成するには大きな本体モデルを 1,000 回、順番に実行する必要があります。NPU は多くの行を同時に計算するのが得意ですが、1 トークンずつの処理では重みの読み出しが支配的になり、その性能を活かしにくくなります。

MTP（Multi-Token Prediction）は、小さな Assistant（ドラフトモデル） で次の数トークンを先に予想し、大きな本体モデルでその予想をまとめて検証する仕組みです。ailia LLM では、Assistant が 3 トークンの候補を作り、本体は「確定済みの 1 トークン + 候補 3 トークン」の 4 行を 1 回の推論（AR-4 グラフ）で評価します。本体の予測と一致した候補はそのまま採用し、最初に食い違った位置では本体の予測したトークンを採用します。

① Assistant が 3 トークンを予想
今日は雨
↓
② 本体が 4 行をまとめて検証（AR-4 を 1 回実行）
今日は雨晴れ
緑: 本体の予測と一致して採用 / 赤: 不一致で破棄 / 紫: 本体が予測したトークン
↓
③ 本体 1 回の実行で 1〜4 トークンが確定
「今日」「は」「晴れ」の 3 トークンが確定し、続きから再び予想します

候補がすべて外れても、本体が予測した 1 トークンは必ず確定します。予想が当たるほど本体の実行回数が減り、生成が速くなります。生成されるトークンは本体の予測に基づいて決まるため、MTP は出力の品質を落とさずに速度を上げる手法です（ただし、AR-4 と AR-1 の数値誤差により、通常生成と完全に同じトークン列になるとは限りません）。temperature を設定したサンプリングでは、本体と Assistant の確率比で候補を受理する方式（Speculative Sampling）を使用し、本体の確率分布に従った出力になります。

実測では、Gemma 4 E2B のテキスト生成で NPU の Decode が Snapdragon 8+ Gen 1 で 1.44 倍、Snapdragon 7s Gen 3 で 1.55 倍、Snapdragon X Plus で 1.50 倍（E4B は 1.70 倍）に向上しました。予想が当たりやすい音声の書き起こしでは 2.5 倍前後になります。

NPU の Decode が CPU を上回る

QNN 単体（AR-1 による 1 トークンずつの生成）では、NPU の Decode は Prefill ほど速くならず、Android 端末でも CPU と同等か下回っていました。MTP では本体の 1 回の実行で複数トークンを確定でき、NPU の並列演算性能を Decode にも活かせるため、Android 端末では CPU と同等以上の速度でトークンを生成できます。Snapdragon 7s Gen 3 の E2B では CPU の 1.63 倍です。

端末・モデル（テキスト生成）CPUNPU（MTP なし）NPU（MTP あり）CPU 比
SM8475（Snapdragon 8+ Gen 1）E2B / FP169.971 tokens/s6.947 tokens/s10.024 tokens/s0.70 倍 → 1.01 倍
SM7635（Snapdragon 7s Gen 3）E2B / Int166.045 tokens/s6.393 tokens/s9.877 tokens/s1.06 倍 → 1.63 倍

音声入力の書き起こしでは、Android の全構成（SM8475 E2B、SM7635 E2B / E4B）で NPU が CPU の 1.55〜2.85 倍の速度になります。NPU は Prefill でも CPU より大幅に高速で、Prefill 中の CPU 使用率も 3% 前後に抑えられるため、MTP と組み合わせることで Prefill・Decode の両方で NPU が有利になります。Snapdragon X Plus のように CPU が高性能な PC では、Decode は依然として CPU の方が高速です。詳細は ベンチマーク を参照してください。

QNN ガイドからの差分

  • ailia LLM 1.5.1 以降が必要です。libailia_llm.so と libailia_llm_qnn.so（Windows では ailia_llm.dll と ailia_llm_qnn.dll）は同じバージョンを組み合わせて配置してください。
  • 本体モデルは MTP 対応版（-mtp.qnn）を使用します。MTP 対応版は従来の AR-256 / AR-1 グラフに加えて、検証用の AR-4 グラフを含みます。
  • 本体を開いた後に、ailiaLLMOpenMtpModel で同じ SoC・モデル・精度の Assistant（-mtp-assistant.qnn）を開きます。
  • その後のプロンプト設定（ailiaLLMSetPrompt / ailiaLLMSetMultimodalPrompt）と ailiaLLMGenerate の使い方は変わりません。ailiaLLMGenerate は MTP でも 1 回の呼び出しで 1 トークンを返し、内部で確定済みのトークンを順に返します。
  • 画像・音声入力の mmproj（-mmproj.qnn）は ailia LLM 1.5.0 向けのファイルをそのまま使用できます。

ファイル名は gemma4-<model>-<soc>-<precision>-mtp.qnn（本体）と gemma4-<model>-<soc>-<precision>-mtp-assistant.qnn（Assistant）です。画像・音声入力には、QNN ガイドに掲載している同じ SoC・モデルの -mmproj.qnn（v1.5.0）を使用します。

MTP 対応の本体は、Assistant を開かなければ従来どおり AR-1 で 1 トークンずつ生成します。MTP の有無を切り替える場合でも、本体ファイルは MTP 対応版の 1 つで済みます。

CPU

CPU では、本体に通常の Gemma 4 の GGUF、Assistant に MTP 用の GGUF を使用します。

モデルファイル内容サイズ

mtp-gemma-4-E2B-it-Q4_0.ggufAssistant（ドラフトモデル）59.2 MB

Assistant は本体と語彙・hidden サイズが一致している必要があります。E2B の本体には E2B の Assistant、E4B の本体には E4B の Assistant を組み合わせてください。

ドラフトモデル（Assistant）を開く API

Assistant は ailiaLLMOpenMtpModel で開きます。

int ailiaLLMOpenMtpModel(struct AILIALLM *llm, const char *path);
引数内容
llm本体モデルを開いた AILIALLM インスタンス
pathAssistant のパス（UTF-8）。NPU の本体には -mtp-assistant.qnn、CPU の本体には mtp-gemma-4-*.gguf を指定します。Windows でも UTF-8 文字列を渡します（W 版はありません）。

呼び出し順は次のとおりです。

  1. ailiaLLMCreate
  2. ailiaLLMOpenModelFileA / W で本体を開く（NPU では -mtp.qnn）
  3. ailiaLLMOpenMtpModel で Assistant を開く（最初のプロンプト設定より前に 1 回だけ）
  4. 画像・音声入力を使う場合は ailiaLLMOpenMultimodalProjectorFileA / W で mmproj を開く
  5. ailiaLLMSetPrompt / ailiaLLMSetMultimodalPrompt と ailiaLLMGenerate で通常どおり生成
  • 失敗した場合はエラーコードを返し、MTP は有効になりません。同じインスタンスで通常の生成は継続できます。
  • MTP 非対応の本体（AR-4 を含まない従来の .qnn）に Assistant を開くと、エラーになります。
  • 一度有効にした Assistant を外したり差し替えたりする場合は、インスタンスを破棄（ailiaLLMDestroy）して作り直します。2 回目の呼び出しは INVALID_STATE になります。
  • NPU の MTP では検証用に 4 トークン分の余裕を確保するため、入力がコンテキスト長 − 4 を超えると、プロンプト設定時に CONTEXT_FULL を返します。

コードサンプル

NPU で SoC 名を取得し、MTP 対応の本体と Assistant を開く例です。モデルファイルはアプリのプライベートストレージにあるものとします。精度（fp16 / int16）は SoC によって異なるため、上記の表に従って選択してください。

C

#include "ailia_llm.h"
#include <stdio.h>
#include <string.h>

/* model_dir: アプリのプライベートストレージ。成功時は呼び出し側が Destroy する。 */
int open_qnn_mtp_model(const char *model_dir, struct AILIALLM **out) {
    if (model_dir == NULL || out == NULL) return AILIA_LLM_STATUS_INVALID_ARGUMENT;
    *out = NULL;
    const char *soc = NULL; /* ライブラリ所有。解放しない */
    int status = ailiaLLMGetQNNModelName(&soc);
    if (status != AILIA_LLM_STATUS_SUCCESS) return status;
    /* sm8475 / sc8380xp は FP16、sm7635 / qcs6490 は Int16 */
    const char *precision =
        (strcmp(soc, "sm8475") == 0 || strcmp(soc, "sc8380xp") == 0) ? "fp16" : "int16";
    char target[512], assistant[512];
    int n1 = snprintf(target, sizeof(target), "%s/gemma4-e2b-%s-%s-mtp.qnn", model_dir, soc, precision);
    int n2 = snprintf(assistant, sizeof(assistant), "%s/gemma4-e2b-%s-%s-mtp-assistant.qnn", model_dir, soc, precision);
    if (n1 < 0 || (size_t)n1 >= sizeof(target) || n2 < 0 || (size_t)n2 >= sizeof(assistant))
        return AILIA_LLM_STATUS_INVALID_ARGUMENT;

    struct AILIALLM *llm = NULL;
    status = ailiaLLMCreate(&llm);
    if (status != AILIA_LLM_STATUS_SUCCESS) return status;
    status = ailiaLLMOpenModelFileA(llm, target, 0);           /* 本体 */
    if (status == AILIA_LLM_STATUS_SUCCESS)
        status = ailiaLLMOpenMtpModel(llm, assistant);         /* ドラフトモデル */
    if (status != AILIA_LLM_STATUS_SUCCESS) { ailiaLLMDestroy(llm); return status; }
    *out = llm;
    return AILIA_LLM_STATUS_SUCCESS;
}

CPU の場合は、本体に GGUF、Assistant に MTP 用 GGUF を指定します。

ailiaLLMOpenModelFileA(llm, "gemma-4-E2B-it-qat-Q4_0.gguf", 4096);
ailiaLLMOpenMtpModel(llm, "mtp-gemma-4-E2B-it-Q4_0.gguf");

CPU の場合は llm.open("gemma-4-E2B-it-qat-Q4_0.gguf") の後に llm.open_mtp_model("mtp-gemma-4-E2B-it-Q4_0.gguf") を呼び出します。失敗時は AiliaLLMError が送出されます。

Unity（C#）

using System;
using System.IO;
using UnityEngine;
using ailiaLLM;

string soc = AiliaLLMModel.GetQNNModelName();

ailiaLLMOpenModelFileA(llm, "gemma4-e2b-sm7635-int16-mtp.qnn", 0);

アーキテクチャ詳細

MTP 対応の本体 .qnn は、Prefill 用の AR-256、検証用の AR-4、通常生成用の AR-1 の 3 つのグラフを 1 つの QNN Context に格納し、重みと KV キャッシュを共有します。Assistant は本体の KV キャッシュと最終層の hidden state を直接参照して候補を生成するため、Assistant 側で KV キャッシュを別に持つ必要がなく、ファイルサイズは 50 MB 未満です。埋め込みテーブルも本体から参照します。

Prefill は従来どおり AR-256 で処理し、最後の hidden state と最初のトークン、KV キャッシュを Assistant に渡します。以降は「Assistant が 3 候補を生成 → AR-4 で 4 行を一括検証 → 受理された分の logits・hidden・KV をそのまま採用」を繰り返します。受理されたトークンの再計算は行いません。確定したトークンは内部のキューに入り、ailiaLLMGenerate の呼び出しごとに 1 トークンずつ返します。

マルチターンで新しいテキストプロンプトを設定すると、未返却の候補を破棄し、安全に再利用できる KV の共通部分を残して続きから Prefill します。画像・音声の切り替え時は、エンコーダ実行前に Assistant を一旦解放し、本体の Prefill 後に再生成します。

制約

  • 本体と Assistant は同じ SoC・モデル・精度の組み合わせで使用してください。他の組み合わせは動作しません。
  • NPU の本体に CPU 用の GGUF Assistant は組み合わせられません。
  • MTP は Decode（トークン生成）を高速化する手法です。Prefill（プロンプト処理）と TTFT はほぼ変わりません。
  • 高速化の度合いは入力の内容とモデルに依存します。音声の書き起こしのように出力が予想しやすい場合は大きく高速化し、E2B の自由な文章生成では 1.4〜1.6 倍程度です。SM7635 の E4B のテキスト・画像入力のように、ほとんど高速化しない場合もあります。
  • CPU の MTP は、モバイル SoC の CPU では Assistant と検証の演算追加に見合う高速化が得られない場合があります（SM7635 の CPU で 0.92 倍）。高速化の効果が大きいのは NPU です。
