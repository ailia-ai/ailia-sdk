ailia LLM MTP (Multi-Token Prediction) Guide

How to speed up Gemma 4 token generation with MTP, supported in ailia LLM 1.5.1.

This page describes the models and API needed for MTP as a delta from the ailia LLM NPU (QNN) Guide. NPU setup (deploying the QNN runtime, Android configuration, getting the SoC name) is the same as in the QNN Guide. For measurements, see the ailia LLM MTP Benchmark.

What is MTP?

An LLM normally generates text one token per inference. Because each token depends on all the tokens before it, generating 1,000 tokens means running the large main model 1,000 times in sequence. NPUs are good at computing many rows at once, but when processing one token at a time, weight loading dominates and the NPU's compute cannot be used effectively.

MTP (Multi-Token Prediction) uses a small assistant (draft model) to guess the next few tokens ahead of time, and then has the large main model verify those guesses all at once. In ailia LLM, the assistant proposes 3 candidate tokens, and the main model evaluates 4 rows ("1 committed token + 3 candidates") in a single inference (the AR-4 graph). Candidates that match the main model's prediction are accepted as is, and at the first mismatch the token predicted by the main model is used instead.

Even if every candidate is rejected, the one token predicted by the main model is always committed. The more guesses hit, the fewer times the main model runs and the faster generation becomes. Because the output tokens are determined by the main model's predictions, MTP increases speed without degrading output quality (however, due to numerical differences between AR-4 and AR-1, the token sequence is not guaranteed to be identical to normal generation). For sampling with temperature, candidates are accepted based on the probability ratio between the main model and the assistant (speculative sampling), so the output follows the main model's probability distribution.

In measurements of Gemma 4 E2B text generation, NPU decode improved by 1.44x on Snapdragon 8+ Gen 1, 1.55x on Snapdragon 7s Gen 3 and 1.50x on Snapdragon X Plus (1.70x for E4B). For audio transcription, where guesses hit easily, the speedup is around 2.5x.

NPU decode outperforms the CPU

With QNN alone (one-token-at-a-time generation with AR-1), NPU decode does not speed up as much as prefill, and even on Android devices it was equal to or slower than the CPU. With MTP, multiple tokens can be committed per main-model run, so the NPU's parallel compute benefits decode as well, and on Android devices tokens are generated as fast as or faster than on the CPU. For E2B on Snapdragon 7s Gen 3, decode is 1.63x the CPU.

The NPU is also much faster than the CPU in prefill and keeps CPU usage during prefill at around 3%, so combined with MTP, the NPU has the advantage in both prefill and decode. On PCs with a high-performance CPU such as Snapdragon X Plus, decode is still faster on the CPU. See the benchmark for details.

Differences from the QNN Guide

  • ailia LLM 1.5.1 or later is required. Deploy libailia_llm.so and libailia_llm_qnn.so (ailia_llm.dll and ailia_llm_qnn.dll on Windows) from the same version.
  • Use the MTP-capable main model (-mtp.qnn). In addition to the AR-256 / AR-1 graphs, it contains an AR-4 graph for verification.
  • After opening the main model, open the assistant (-mtp-assistant.qnn) for the same SoC, model and precision with ailiaLLMOpenMtpModel.
  • Setting prompts (ailiaLLMSetPrompt / ailiaLLMSetMultimodalPrompt) and calling ailiaLLMGenerate work the same as before. Even with MTP, each ailiaLLMGenerate call returns one token, delivering committed tokens in order from an internal queue.
  • The mmproj (-mmproj.qnn) for image and audio input from ailia LLM 1.5.0 can be used as is.

API for Opening the Draft Model (Assistant)

Open the assistant with ailiaLLMOpenMtpModel.

int ailiaLLMOpenMtpModel(struct AILIALLM *llm, const char *path);
ArgumentDescription
llmThe AILIALLM instance in which the main model has been opened
pathPath to the assistant (UTF-8). Specify -mtp-assistant.qnn for an NPU main model, or mtp-gemma-4-*.gguf for a CPU main model. Pass a UTF-8 string on Windows as well (there is no W variant).

Call the APIs in the following order.

  1. ailiaLLMCreate
  2. Open the main model with ailiaLLMOpenModelFileA / W (-mtp.qnn on the NPU)
  3. Open the assistant with ailiaLLMOpenMtpModel (only once, before setting the first prompt)
  4. For image or audio input, open the mmproj with ailiaLLMOpenMultimodalProjectorFileA / W
  5. Generate as usual with ailiaLLMSetPrompt / ailiaLLMSetMultimodalPrompt and ailiaLLMGenerate
  • On failure, an error code is returned and MTP is not enabled. Normal generation can continue with the same instance.
  • Opening an assistant on a main model without MTP support (a conventional .qnn without AR-4) returns an error.
  • To remove or replace an enabled assistant, destroy the instance (ailiaLLMDestroy) and create a new one. A second call returns INVALID_STATE.
  • NPU MTP reserves 4 tokens of headroom for verification, so if the input exceeds the context length minus 4, setting the prompt returns CONTEXT_FULL.

Code Samples

These examples get the SoC name on the NPU and open the MTP-capable main model and assistant. The model files are assumed to be in the app's private storage. The precision (fp16 / int16) depends on the SoC; choose it according to the table above.

C

#include "ailia_llm.h"
#include <stdio.h>
#include <string.h>

/* model_dir: the app's private storage. On success, the caller must Destroy. */
int open_qnn_mtp_model(const char *model_dir, struct AILIALLM **out) {
    if (model_dir == NULL || out == NULL) return AILIA_LLM_STATUS_INVALID_ARGUMENT;
    *out = NULL;
    const char *soc = NULL; /* owned by the library; do not free */
    int status = ailiaLLMGetQNNModelName(&soc);
    if (status != AILIA_LLM_STATUS_SUCCESS) return status;
    /* sm8475 / sc8380xp use FP16, sm7635 / qcs6490 use Int16 */
    const char *precision =
        (strcmp(soc, "sm8475") == 0 || strcmp(soc, "sc8380xp") == 0) ? "fp16" : "int16";
    char target[512], assistant[512];
    int n1 = snprintf(target, sizeof(target), "%s/gemma4-e2b-%s-%s-mtp.qnn", model_dir, soc, precision);
    int n2 = snprintf(assistant, sizeof(assistant), "%s/gemma4-e2b-%s-%s-mtp-assistant.qnn", model_dir, soc, precision);
    if (n1 < 0 || (size_t)n1 >= sizeof(target) || n2 < 0 || (size_t)n2 >= sizeof(assistant))
        return AILIA_LLM_STATUS_INVALID_ARGUMENT;

    struct AILIALLM *llm = NULL;
    status = ailiaLLMCreate(&llm);
    if (status != AILIA_LLM_STATUS_SUCCESS) return status;
    status = ailiaLLMOpenModelFileA(llm, target, 0);           /* main model */
    if (status == AILIA_LLM_STATUS_SUCCESS)
        status = ailiaLLMOpenMtpModel(llm, assistant);         /* draft model */
    if (status != AILIA_LLM_STATUS_SUCCESS) { ailiaLLMDestroy(llm); return status; }
    *out = llm;
    return AILIA_LLM_STATUS_SUCCESS;
}

On the CPU, specify a GGUF for the main model and the MTP GGUF for the assistant.

ailiaLLMOpenModelFileA(llm, "gemma-4-E2B-it-qat-Q4_0.gguf", 4096);
ailiaLLMOpenMtpModel(llm, "mtp-gemma-4-E2B-it-Q4_0.gguf");

Python

from pathlib import Path
import ailia_llm

soc = ailia_llm.AiliaLLM.get_qnn_model_name()
precision = "fp16" if soc in ("sm8475", "sc8380xp") else "int16"
model_dir = Path("/data/user/0/your.package/files")

llm = ailia_llm.AiliaLLM()
llm.open(str(model_dir / f"gemma4-e2b-{soc}-{precision}-mtp.qnn"), n_ctx=0)
llm.open_mtp_model(str(model_dir / f"gemma4-e2b-{soc}-{precision}-mtp-assistant.qnn"))

for delta in llm.generate([{"role": "user", "content": "Introduce yourself."}]):
    print(delta, end="", flush=True)

On the CPU, call llm.open_mtp_model("mtp-gemma-4-E2B-it-Q4_0.gguf") after llm.open("gemma-4-E2B-it-qat-Q4_0.gguf"). On failure, AiliaLLMError is raised.

Architecture Details

The MTP-capable main .qnn stores three graphs in a single QNN context — AR-256 for prefill, AR-4 for verification and AR-1 for normal generation — sharing the weights and the KV cache. The assistant generates candidates by directly referencing the main model's KV cache and final-layer hidden state, so it does not need its own KV cache and its file size is under 50 MB. The embedding table is also referenced from the main model.

Prefill is processed with AR-256 as before, and the last hidden state, the first token and the KV cache are passed to the assistant. After that, the cycle "the assistant generates 3 candidates → AR-4 verifies 4 rows at once → the logits, hidden states and KV for the accepted part are adopted as is" repeats. Accepted tokens are not recomputed. Committed tokens enter an internal queue, and each ailiaLLMGenerate call returns one token.

When a new text prompt is set in a multi-turn conversation, pending candidates are discarded, the common KV prefix that can be safely reused is kept, and prefill continues from there. When switching between image and audio, the assistant is released before running the encoder and recreated after the main model's prefill.

Limitations

  • Use the main model and assistant as a pair for the same SoC, model and precision. Other combinations do not work.
  • A CPU GGUF assistant cannot be combined with an NPU main model.
  • MTP speeds up decode (token generation). Prefill (prompt processing) and TTFT are largely unchanged.
  • The speedup depends on the input and model. When output is easy to predict, as in audio transcription, the speedup is large; for free-form E2B text generation it is around 1.4x to 1.6x. In some cases, such as text and image input with E4B on SM7635, there is almost no speedup.
  • On mobile SoC CPUs, CPU MTP may not gain enough to offset the extra assistant and verification compute (0.92x on the SM7635 CPU). The NPU is where MTP is most effective.
